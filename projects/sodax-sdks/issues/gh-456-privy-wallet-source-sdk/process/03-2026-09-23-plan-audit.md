# Session 03 — audit of the plan itself: approach, over-engineering, bug risk

No new research and no code. This session took `plan.md` rev 2 as the **thing under test** and
asked three questions: is the approach right, is it over-built, and where will the bugs actually
come from. Every repo claim below was re-checked against `origin/main` in this session; every
`@privy-io/*` claim was **not** (see § Unverifiable here).

## Verdict

The core architectural call is right and well-evidenced. The plan is **over-planned at the
document layer and over-exposed at the public-API layer**. One factual error found, one feature
recommended for outright removal, one settled choice worth re-opening before code starts.

## What holds up

**"Privy is one more wagmi connector, not a provider swap" is correct**, and it is the decision
that saves the feature. Re-read `EvmProvider.tsx:33-42` this session: it builds a `connectors`
array and hands it to `createWagmiConfig`. `@privy-io/wagmi` replaces that array (F2), so
WalletConnect and EIP-6963 die and AC5 cannot hold. Everything downstream of this call is sound.

**Four of the rev-2 bug catches are real, and all four are silent failures** — the kind that ship:

| Bug rev 1 would have shipped | Re-verified this session |
| ---------------------------- | ------------------------ |
| `isAuthorized()` comparing a Promise to `true` — type-checks clean, permanently `false` | `@wagmi/core` wraps every store in `async getItem` |
| Reconnect flag in `config.storage` dies on browser quit while the zustand entry survives | `EvmXService.ts:139-141` = `cookieStorage`; `useXWalletStore.ts:155` = `localStorage`. Confirmed divergence |
| `getChainId()`/`getAccounts()` disagreement → `ConnectorChainMismatchError` cached at `staleTime: Infinity` | `EvmHydrator.tsx:52-57` carries a comment saying it **deliberately does not gate on `walletClient`** — so the UI shows connected while `useWalletProvider('EVM')` stays `undefined`, no error surfaced. The plan read the right code |
| `setup()` listener leaking through StrictMode's double-invoked `useMemo` | plausible from the wagmi contract in F1; not independently re-run |

**Fail-closed on account change** (detach rather than follow a new address) is the right call for
an intent-signing SDK. **Precedents were read and rejected with reasons** (pinto-org's
`isAuthorized()` reading a React closure; gap-app-v2 hardcoding `return true`) rather than copied.

## Error found in the plan

`plan.md` § Steps → Step 0 states: *"`pnpm build:packages` runs zero tasks — the turbo task exists,
no package implements the script; use `pnpm build`."* The same claim is a landmine row in
`brief.md`.

**This is wrong.** `turbo.json:27` declares `build:packages` with `dependsOn: ["^build"]`, so
`pnpm turbo run build:packages --dry` schedules **26 tasks, 8 of them real `build` commands**
(`@sodax/types`, `wallet-sdk-core`, `wallet-sdk-react`, `sdk`, `libs`, `dapp-kit`, `bridge-api`,
`swaps-api`). The task's own `Command` is `<NONEXISTENT>`, which is what the earlier reading saw,
but the dependency graph still runs. `build:packages` does exactly what its name says and is
**lighter** than the recommended `pnpm build`, which also builds the apps.

Corrected in `brief.md` this session. The wider lesson: this was recorded as a verified fact and
it was not one.

## Recommended cuts — five

1. **Three parallel plan documents, two stale by construction.** `plan.md` (66 KB) +
   `plan-architecture.md` (51 KB) + `plan-revision-2.md` (89 KB). `plan-architecture.md` is a
   *second complete plan* (mount trees, public API, test plan, ACs, risks, open questions — all
   duplicated), and `plan-revision-2.md` is a diff against rev 1 that has **already been applied**
   to `plan.md`. Anyone opening `plan-architecture.md` reads rev-1 thinking that rev 2 refuted.
   → Keep `plan.md`. Reduce the other two to a short decisions log, or mark them archived in the
   brief's map with the token cost of reading them by mistake.
2. **Four timeout knobs as public API** (`readyTimeoutMs`, `connectReadyTimeoutMs`,
   `walletTimeoutMs`, `providerTimeoutMs`). Distinguishing the four phases is *correct* — a login
   modal must never be timed out while a readiness wait must be — but that is an argument for four
   **internal constants**, not four public options. No partner has asked. A public knob is
   permanent. → Expose zero or one in V1.
3. **Five exported error classes.** Only `PrivyConnectorSupersededError extends
   UserRejectedRequestError` is load-bearing (wagmi's catch depends on the type). The rest are
   diagnostics no partner will `instanceof`. → Keep the classes, drop the exports.
4. **`sessionProbe.ts`**, specified as "optional and mount-gate only — never consulted by
   `isAuthorized()`": a module that exists and is explicitly forbidden at the one place it looks
   useful. → Cut.
5. **Late-readiness self-`reconnect()` — cut outright in V1.** This is where a real bug will come
   from: re-entering wagmi's reconnect after its loop has settled, guarded on three heuristic
   conditions (flag ∧ `!config.state.current` ∧ `!userDisconnected.EVM`), racing an internal
   wagmi field. The plan writes its own fallback in the same paragraph — *"one click on Email
   (Privy) reconnects with no second OTP via branch 2"* — which is acceptable UX and zero code.
   → Ship the fallback, document it.

Net: the plan kept generating surface (options, error types, modules, build scripts) past the
point of diminishing returns. The actual deliverable is ~7 small modules, one error boundary, two
build scripts and two test files.

## Residual bug risk, ranked

1. **Late-readiness `reconnect()`** — cut it (above).
2. **Account-change watcher.** A polling-shaped invariant over a React state stream: wallet-object
   identity compare, transient null-`user` ticks, pinned-address disappearance. The plan is aware
   of each; it needs exactly the fake-runtime tests it specifies, and those are not optional.
3. **`supportedChains` decoration across all 14 chains.** The plan says "separate array, never
   mutate the shared tuple" — correct, and the same `Chain` objects feed `createWagmiConfig`'s
   `transports`, so getting it wrong corrupts the read path too, not just Privy's.
4. **Supersession guard via an injected `getWagmiState`.** Reaching into `config.state.current` is
   a wagmi-internals dependency; it will break on a wagmi bump and nothing will fail loudly.

**Kept despite looking intricate:** the four-step chain switch with `pendingRuntimeChainId`. The
plan demonstrates rev 1's simpler version was a guaranteed race (`embedded.switchChain` is a React
`setState`; `getEthereumProvider()` mints a provider pinned to the chain captured in the render
that produced the wallet object). The complexity is earned.

## Re-open before code starts: does `EVM.privy` deserve to exist?

`plan.md` § Out of scope says: *"once #163 lands, `EVM.wagmiConnectors` is the public generic
extension point, so #456 must not add a second one"* — but `EVM.privy` **is** that second one.
The stated defense (the host needs `EvmTypeConfig['chains']` to inject `privyWalletOverride`)
justifies the **Host**, not a provider-named **connector slot**.

Leaner shape worth costing: `EVM.wagmiConnectors` (or plain `connectors` until #163 lands) plus a
single generic `EVM.hosts?: ComponentType[]`. One seam instead of two, and no provider name baked
into public API — which cannot be removed later.

This is live, not theoretical: **#163 is still OPEN and was updated 2026-09-21**, so it may well
land first.
