### `normalizeAndValidateScrapeTarget` throws 4 times, not 5

The ticket says five throws at `scrape.ts:161-182`. The function has **four**:

### Only 2 of 17 `checkRateLimit` call sites pass an email

This is what forced the whole-email gate rather than an `includes('@')` check.

| identifier kind | sites |
| --- | --- |
| email | 2 — `email-guide:recipient`, `inquiry:sender` |
| client IP | 9 |
| `'global'` | 4 |
| registered domain | 1 — `analyze:domain` |
| error-signature hash | 1 — `brand/download-error` dedupe |

That last one is the trap: the signature is built from status/statusText/message/page/**userAgent**,
and a user-agent can contain `@`.

### `releaseRateLimit` rebuilt the key independently

`checkRateLimit` built `` `${scope}:${identifier}:${windowStart}` `` at `:137`;
`releaseRateLimit` built the same string again at `:202`. Canonicalising in only one of them
would have made every release miss its row. Today's single `releaseRateLimit` caller passes
an error signature rather than an email, so nothing was broken in practice — but the two had
to be merged into one helper before touching either.

### `getProtocolName` never throws

`lib/lead-magnet/url.ts:108-118` catches its own `new URL()` failure and falls back to
echoing its input. Safe here because it is only ever handed an already-normalised URL. Also
already the server-side source of the name in `analyze/route.ts:607`, so this change makes
the two routes agree rather than inventing a new convention.

### No client sends `protocolName` to this route

Grepped the whole app. The field was accepted and used, but nothing in `apps/web` populates
it for `/api/partners/email-guide` — the guide pages read `guide.protocolName` off the
**stored** guide, which analyze already writes as `getProtocolName(safeUrl)`. So dropping it
from the request shape is a no-op for first-party callers and closes the hole for everyone else.

### The repo has no test suite at all

Zero `*.test.*` / `*.spec.*` files, no vitest/jest/playwright config, and no workspace
defines a `test` script — `pnpm test` is a no-op and **CI never runs it**
(`ci.yml:40-49` is install → lint → checkTs → build). So the canonicaliser was verified by a
scratchpad driver that extracts the real function bodies out of the shipped file and
exercises them, rather than by a committed unit test. 14/14 cases pass:

```
a@x.com / a+1@x.com / A@X.com          -> one key           (bypass closed)
a+anything+else@x.com                  -> a@x.com
a.b@gmail.com / a.b@googlemail.com     -> ab@gmail.com
a.b@fastmail.com                       -> unchanged         (dots only fold for Google)
1.2.3.4 / global / example.com         -> unchanged
"Mozilla/5.0 (X11) foo@bar baz"        -> unchanged         (the user-agent trap)
buildRateLimitId agrees across check/release
```

### 15 typecheck errors that turned out to be local rot

First `pnpm checkTs` reported 15 errors — missing modules (`sharp`, `posthog-node`,
`pdfjs-dist`, `unified`, `remark-*`), an SDK export mismatch, and stale `.next/types`.
**None named the two changed files.** `pnpm install --frozen-lockfile` cleared 9 of them
(stale install); the remaining 6 were generated types under `.next/types/**` still
referencing `app/consensus-miami`, a route deleted upstream. Removing `.next/types` (fully
regenerated by `next build`) left the typecheck **completely green**. Nothing to fix in the
repo — a clean CI checkout never sees this.
