Title: `feat: ship the logs to unified logging over OTLP`

Closes #110.

With `OTEL_LOGS_ENABLED=true`, every log record the server writes to stderr also goes to SODAX unified logging over OTLP (protobuf, bearer token), with the resource attributes the gateway requires. Nothing changes without the variable: the OpenTelemetry modules load only when it is set.

What a record carries:

- `request.id`: one per HTTP request (or per tool call over stdio), on every record it produces, transport-level ones included, so a swap can be followed from the agent's call through each backend and chain call to the answer.
- One `HTTP request` record per `/mcp`, `/messages` and `/sse` request, the ones a guard refuses included: `http.request.method`, `http.route`, `http.response.status_code` (absent when the client left before the answer), `duration.ms`, `mcp.method.name` (the SDK's own method list, anything else `other`), `client.ip_hash` when `POSTHOG_CLIENT_ID_SECRET` makes it an HMAC, `error.type` naming the guard that refused it (`UNKNOWN_PROFILE`, `API_KEY_REQUIRED`, `SSE_SESSION_LIMIT`, `INVALID_JSON`, ...), `mcp.profile`, `caller.key_status` and `caller.key_hash` (never the key), `user_agent.original`, and on `initialize` the client's `mcp.client.name`, `mcp.client.version` and `mcp.protocol.version`. The request context opens in that middleware, so this record and every other one of the request share the id. A limiter logs `Rate limited` once per client per window (a batch that crosses the line counts like a single request; the route is one of this server's, never a path a client typed); its 429 request records stay at debug, so a flood can't write the log (the SSE cap's 429 is no limiter's and stays at info). A call the SDK refuses before any handler runs (unknown tool, invalid arguments) gets its `Tool call` record too, named only when the tool exists (a swap tool called without a key keeps its name).
- One record per step, with dotted attributes: the tool call (`gen_ai.tool.name`, `tool.outcome`, `error.type`, `duration.ms`, `caller.key_hash`, and for the swap tools `swap.status`, `quote.id`, `tx.hash`, `hub_tx.hash`, `intent.hash`, `chain.key`, `dst_chain.key`, `swap.usd_bucket`), each upstream call, written once its body is read so a body that never arrives is a failed call (`http.request.method`, `server.address`, `url.template` as its route: a data API call by its template from the drift-checked contract, static segments kept and parameters masked; any other path with every segment from the fifth on masked and, before that, any that isn't a plain lowercase word, `http.response.status_code`, `duration.ms`; the relay included), each chain read (`sdk.call`, `chain.key`, `duration.ms`).
- One failure, one record of each kind: the data services no longer log their own `Failed to fetch …` errors, a failed chain read and an unexpected swap-tool error aren't logged twice. A data or docs tool's failure gets an `error.type` from its cause (`UPSTREAM_NOT_FOUND`, `UPSTREAM_4XX`, `UPSTREAM_5XX`, `UPSTREAM_TIMEOUT`, `UPSTREAM_UNREACHABLE`, `UPSTREAM_BAD_RESPONSE`, `INVALID_INPUT`, …) without changing what the agent receives, and the `Tool call` level says whose failure it is: info for the caller's, warn for SODAX's side, error for a bug. Record bodies are constants; what varies is in attributes.
- The request's id comes back in an `X-Request-Id` response header, for a builder to quote, and goes out in the same header on calls to SODAX's API hosts, so their logs can name it once they read it; the API key rule is unchanged. The boot drift check writes its report as one warning (`details`) instead of a record per line, and `pnpm check:drift` prints it a line each.
- Every record uses the same dotted keys, swap records and operator alerts included (`chain.key`, `dst_chain.key`, `quote.id`, `tx.hash`, `upstream.*`), so a swap's `quote.id` or `tx.hash` finds its deposit, mismatch and alert records too, and an alert's `caller.key_hash` matches the Tool call's. Discord keeps its own field names.
- A `Unified logging heartbeat` record every 5 minutes with the export counts and the server's gauges (open swap quotes and SSE sessions, memory, event-loop delay p99, swap catalog age, docs proxy health), through the logger at info whatever `LOG_LEVEL` is, so sodax-observability's producer-liveness alert (10 silent minutes) doesn't page for a quiet server.
- A boot record (`SODAX Builders MCP server started`: transport, version, `sodax.env`, swap tools on or off, the chains with an RPC override, whether PostHog and Discord are set, log level), `SSE session opened` with a hash of the session id (also on that session's `GET /sse` and `POST /messages` records), and `Swap quote expired unused` for each quote the cache drops without a deposit (a one-minute sweep; `quote.drop_reason` `expired` or `evicted`).
- Names follow the OpenTelemetry semantic conventions where one exists (HTTP, `url.template`, `server.address`, `error.type`, MCP's `mcp.method.name` and `gen_ai.tool.name`); `SeverityText` is lowercase (`info`, `warn`, `error`), as the backend's winston levels arrive, so the explorer's severity filter has one value per level. The README has the record catalog to write alerts against.
- The same redaction stderr gets: no RPC URL, request body, API key or private key leaves the process. Errors arrive as `exception.type/message/stacktrace`; a tool that throws (tools return their failures as `isError`, so a throw is a bug) logs its class and stack frames at `error` level, never its message.

How it is built: pino's `streamWrite` hook hands each serialized line to an OTLP destination (`src/services/otel.ts`) that parses it once more and emits it through a bounded `BatchLogRecordProcessor` (queue 4096, batch 512, 5 s). A gateway outage drops records and never slows a tool call; the SDK's own complaints are logged once per message per five minutes and never shipped. A stop flushes what the batch holds; a crash tries within its one-second window. `GET /health` reports `unifiedLogging` (on, records written, exported and failed, the last failure time), so a token or allowlist problem shows there before Grafana (a batch the gateway accepted but partly rejected counts as exported and is logged as a warning). A record cut at the attribute limit carries `log.attributes_truncated` and keeps room for the exception's attributes. The route templates come from the drift check's contract and are checked against it, and a test fails if the API client builds a path the contract doesn't have; the Swaps API's failure records use the same `url.template` and `http.response.status_code`, with ids in the upstream message masked; `error.type` takes only code-shaped values, from the error or its cause.

Env (README table, `.env.example`): `OTEL_LOGS_ENABLED`, `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` (the `/v1/logs` URL, used as given, or the gateway's bare origin, which gets `/v1/logs` appended as the backend does; a trailing slash is dropped; https unless `DEPLOYMENT_ENV=dev`), `OTEL_LOGS_TOKEN` (secret, deployment env only), `DEPLOYMENT_ENV` (`prod`, `canary`, `staging`, `dev`), `ORIGIN` (optional). `service.version` is the running commit (`GIT_SHA`, which the image sets from Coolify's `SOURCE_COMMIT` build argument), else the package version; a blank `HOSTNAME` falls back to the host name, since the gateway drops a record with an empty `service.instance.id`. A missing or bad one warns once at boot and leaves shipping off, and so does a failure to start: the server still serves; so does an `OTEL_EXPORTER_OTLP_HEADERS` / `_LOGS_HEADERS` in the env, since the server sends only its own Authorization header. `DEPLOYMENT_ENV` is independent of `SODAX_ENV`: the test server runs canary with `staging`.

Dependencies, pinned: `@opentelemetry/api` 1.10.0, `@opentelemetry/sdk-logs` 3.0.0, `@opentelemetry/exporter-logs-otlp-proto` 0.300.0, `@opentelemetry/resources` 3.0.0 (released 2026-10-20). They need Node 22.15, so `engines.node` and the README say so; the image is `node:22-alpine`.

`intent.hash` is the hub's id of the intent (keccak256 of the `createIntent` struct, what `GET /intent/:intentHash` and the solver use), computed from the struct the server already holds with the SDK's `getIntentHash` and checked against the data API's own hashes; the quote, track and cancel results expose it as `intentHash` too.

Differences from the issue, on purpose: `request.id` is the HTTP request's (a JSON-RPC batch shares it; the `/mcp` transport is stateless, so there is no session id) and a stdio tool call mints its own; upstream calls use the OTel names (`server.address`, `http.response.status_code`) instead of `upstream.service`/`upstream.status`; the swap's hub transaction is `hub_tx.hash` (no tool emits an intent hash); nothing from the tool arguments is logged, and ids in upstream paths are masked; `ORIGIN` is optional, as the gateway's guide says; Injective and the docs proxy stay out.

Tested: `checkTs`, lint, build, unit tests (1060; the new ones in `otel.test.ts` and the extended `logger`, `http`, `analytics`, `sodax` and `index` tests all fail on the previous code). Live, with the built server against the sodax-observability stack run locally in Docker (its own smoke test green): records land in ClickHouse with the required resource attributes and pass the ingest filter, one call's records share a `request.id`, no key-shaped text is stored, and the stop flush lands; that run found the collector redacts `api*key`-named attributes, hence `caller.key_hash`. Rerun with the gateway's current collector config: a canary quote and its track share `quote.id` and `intent.hash`, the heartbeat lands after five minutes, and the liveness query skips this namespace's `dev`. Full report: https://github.com/gosodax/builders-sodax-mcp-server/issues/110#issuecomment-6763412786. Against a local sink: records arrive as protobuf with the bearer header at boot, after a request and on SIGTERM; a sink answering 500 produces one warning and `/health` stays 200; a wrong `DEPLOYMENT_ENV` warns once and ships nothing; the `pino-pretty` development path ships too.

The gateway side is in place (the `prod`, `staging` and `dev` tokens and the test server on the allowlist). Before records ship from the test server, its env needs `OTEL_LOGS_ENABLED=true` and `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` next to the token and `DEPLOYMENT_ENV=staging`; Coolify's "Include Source Commit in Build" makes `service.version` the commit. Then a quote + track visible in Grafana under one `request.id`.
