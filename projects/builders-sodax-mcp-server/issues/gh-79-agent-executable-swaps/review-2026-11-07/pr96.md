# #96 pre-review (2026-11-07)

Tip `feat/86-get-balance` @ `3b038e0`; unchanged at #102 `c665c75`. 650 unit tests pass on Node 24. R0bi7's NEAR
point is real and is the main blocker. It's a bug in this server, not the SDK.

## R0bi7's point: confirmed

Code path (verified in code):

- `balance.ts:70` runs the native read and the token read together (`Promise.allSettled`).
- `sodax.ts:242-252` (`walletBalance`) turns NEAR's `AccountDoesNotExistError` on the native read into `null`.
- `balance.ts:76-78` then returns `token: holding(asked, 0n)` and never awaits the token read. The comment there
  says "An account that doesn't exist holds nothing", which is false on NEAR.

Why it's wrong on NEAR:

- The SDK reads a NEP-141 balance with `ft_balance_of` on the token contract, keyed by the account-id string. The
  holder's account doesn't need to exist.
- Live check: implicit account `6c3914c0009cb2c3bc82bc1ee7f9c36dfd777906db2958b607287877338b9ade` has no account
  (`view_account` returns UNKNOWN_ACCOUNT). Its USDC `ft_balance_of` is 25000100000 (25,000.1 USDC), and storage is
  registered for it. Through the PR's `readBalances` it comes back native 0, USDC "0", `accountExists:false`, next
  step "holds nothing there". (Balance can move; re-check before quoting it in a test.)

Second effect (throwaway vitest): NEAR native `null` and the USDC read fails ("rpc down") → `isError` false with
USDC "0". An RPC failure looks like a zero balance, breaking the PR's own "never 0" rule.

Failure scenario: a swap delivers USDC to a fresh NEAR implicit account. The quote's recipient check passes
(storage registered). Track tells the agent "sodax_get_balance on the recipient shows it arrive". The tool reports
0 USDC and "holds nothing", so the agent tells the user the funds never arrived.

Fix (`balance.ts:76-79`): zero the token only on Stellar (a Stellar account that doesn't exist has no trustlines;
the catalog's Stellar tokens behave like SACs: the issuer reads i64::MAX). Everywhere else, use the token's own read:

```ts
if (nativeRead.value === null) {
  const missing = { ...base, native: holding(native, 0n), accountExists: false as const };
  if (!asked) return missing;
  // A Stellar account that doesn't exist has no trustlines; NEP-141 balances live in the token contract.
  if (!token || chainType === "STELLAR") return { ...missing, token: holding(asked, 0n) };
  return { ...missing, token: holding(token, await tokenUnits) }; // a failed read stays CHAIN_UNAVAILABLE
}
```

What the agent should see: `status:"ok"`, native `0 NEAR`, token `25000.1 USDC`, `accountExists:false`, next step
like "The wallet has no NEAR account yet (0 NEAR) but holds 25000.1 USDC; it needs NEAR to pay gas there." If the
token read fails: `CHAIN_UNAVAILABLE`.

Text updates with the fix: the `accountExists` doc at `balance.ts:29` and the comment at `:77`; `swap.ts:175-177`
(`:199-201` at #102); the PR body bullet "(an unfunded Stellar or NEAR account) is reported as holding nothing".

Tests:

- In `swapBalance.test.ts`, add a `withNear()` catalog (the fixture has no NEAR).
- (a) NEAR native `null`, USDC `25_000_100_000n` → `token.baseUnits` "25000100000", `accountExists:false`, next step
  without "holds nothing".
- (b) NEAR native `null`, USDC rejects → `isError`, `CHAIN_UNAVAILABLE`.
- Rename `:133` to be Stellar-only; it claims more than its single Stellar case covers.
- Contract test: a random 64-hex implicit account gives `accountExists:false` (a live holder can be added, but its
  balance moves).

## Same class on other chains (SDK source + live reads)

- Stellar, missing account → token 0: correct.
- Stellar, existing account without a trustline: 22 catalog xStocks (AMC, NFLX, GLD, …) are missing from
  `trustlineConfigs` in `@sodax/types` 2.2.0. Live: `GDZZZV63F63EL63XSKXE6V535JYUW2WFO6VKLYH73LCOUJCUCDRFPNIW` with AMC
  gives `CHAIN_UNAVAILABLE` ("Couldn't read Stellar right now"); the same account reads bnUSD, SODA and NVDA right
  (0 with `trustline:false`). Root cause is in the SDK: `hasSufficientTrustline` throws "Trustline config not
  found", and `getWalletBalance` throws on a missing trustline instead of returning 0n. Until the SDK is fixed,
  keeping an error is safe, but the MCP shouldn't present it as temporary: check `trustlineConfigs` (plain packaged
  data) and return an error that doesn't invite a retry. Same cause makes quotes to these tokens fail at
  `checkRecipient` (see `pr93-94.md` finding 1). File the SDK bug in sodax-sdks.
- Correct 0 for an empty account, checked live: Solana wallet without the ATA (both token programs), unfunded Sui
  address, fresh Injective, fresh ICON `hx`, fresh Bitcoin.
- RPC errors propagate on every other chain; the single-token path has no catch turning a failure into 0, and the
  MCP already blocks Bitcoin's non-native 0n.
- One failing read fails the whole call, so a good native read is lost when the token read fails. Safe; partial
  results are optional.

## Checked and fine

- No RPC URL leaks: `walletBalance` and `recipientReady` go through `bounded`; `chainRead` logs only `chainKey` and
  `op`; the only SDK log on these paths ("No token balances found for token: C…") has no URL.
- Cache keyed by chain, address as typed, token address. Data doesn't depend on any API key; failed reads are
  dropped; eviction is sound.
- Units: for every catalog chain the catalog's native address equals the SDK's `nativeToken` (live). Hedera's 8
  decimals come from the SDK's scaling; Stacks returns bigints.
