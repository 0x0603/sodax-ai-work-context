## R0bi7's #93 point: confirmed, still at #102

- Where: `src/services/swap/resolver.ts:97-106` on #93 (`:150-161` on #102). The cross-chain hint skips native
  tokens with `!byAddress.isNative`, but `isNative` is set only from the live chain config's `nativeToken`
  (`tokens.ts:154,161`). A chain with no config, or a config with no `nativeToken`, has its `0x000…0` token marked
  `isNative: false`, and the catalog is still served (`tokens.test.ts` "serves a catalog where some chains have no
  native mark" keeps that case on purpose).
- Failing input, run:
  - Fixture without the `hyper` config, `resolveToken(catalog, "ICON", 0x000…0)`: returns
    `otherChains: [hyper/HYPE]`, nextStep "No swap token on ICON matches that; it is HYPE on HyperEVM. Confirm the
    chain with the user…".
  - Without `nativeToken` on hyper and avax, query on Sui: "it is HYPE on HyperEVM, AVAX on Avalanche".
- Why it's wrong for an agent: the zero address is the gas token of every EVM chain, yet the agent tells the user it
  is HYPE, and the chain it names is exactly the one with broken metadata.
- `0xEeee…` takes the same path but no live chain lists it today, so it doesn't show yet.
- Minimal fix: when the query is a sentinel, don't match by address on other chains.

  ```ts
  const sentinel = /^0x0{40}$/.test(q) || q.toLowerCase() === EVM_NATIVE_PLACEHOLDER;
  const byAddress = sentinel ? undefined : findToken(catalog, other, q);
  ```

  Tried in a scratch worktree: the wrong hint goes away, 81 resolver/swap tests still pass.
- Test: next to `resolver.test.ts:189`. Build the catalog with `parseCatalog` from fixture configs without `hyper`,
  plus a case that keeps `chain` but drops `nativeToken`. Expect `resolveToken(partial, "ICON", zero)` to have no
  `otherChains`.
- Other places checked: balance (#96) refuses when there's no native (`balance.ts:47-49`), fine. Track doesn't use
  `isNative`. `findToken`, `packagedToken`, `usdValue` and the restricted-token rule are all gated by chain. Only the
  quote shares this `isNative` source (nit 3).

## New findings

1. should-fix (lowest #94, unchanged at #102): the Stellar recipient check reports deterministic failures as
   "service down".
   - Where: `src/services/swap/destination.ts:37-43`. Every `recipientReady` error becomes `UPSTREAM_UNAVAILABLE`
     with nextStep "Retry in a minute… service is unavailable". Two cases are deterministic, not network errors:
     - SDK 2.2.0 `hasSufficientTrustline` throws "Trustline config not found" for tokens missing from
       `trustlineConfigs`. Live snapshot 2026-11-07: 22/66 Stellar tokens (AMC, NFLX, GLD, JNJ…). Every ready quote
       to these tokens fails.
     - Recipient not funded: Horizon 404 (`NotFoundError`), same error.
   - Run: the real `checkRecipient` gives `UPSTREAM_UNAVAILABLE` for both. The agent retries, then tells the user
     SODAX is down.
   - Fix: 404 → `DESTINATION_NOT_READY` (account doesn't exist; reuse `isMissingAccount` already in `sodax.ts` at
     #102). Missing trustline config → a non-retry refusal, e.g. "can't verify this token's recipient". Root cause
     of the config gap is in the SDK (`@sodax/types` `trustlineConfigs`): file it there too.
2. should-fix (lowest #94, at #102 `sodax.ts:124`): an all-uppercase partner address is accepted, but the SDK drops
   the fee.
   - Where: `partnerFee.ts:21-26` with `sodax.ts:95`. `checksumValid` treats `hex === hex.toUpperCase()` as valid,
     while viem `isAddress` (strict) returns false, so `createIntentFeeData` returns `["0x", 0n]`.
   - Run through the repo's stub (which builds the intent with the same SDK as the live API): the connection is
     accepted, every ready quote gives `SWAP_MISMATCH` (`inputAmount`) with "don't retry", and it's logged as if
     upstream were compromised. Live backend behavior inferred from the SDK, not called live.
   - The PR body says "EIP-55 checksummed or all lowercase"; the code is looser.
   - Fix: drop the `toUpperCase` branch, or normalize with `getAddress`. Test: an uppercase address gets 400.
3. nit (lowest #94; `quote.ts:190`, `:244` at #102): the native-token approve skip has no guarding test.
   - It relies on `isNative` from the live config.
   - Mutation: deleting `from.token.isNative ||` keeps 100/100 swapQuote tests green. The test "skips the approve …
     (a native token)" (`swapQuote.test.ts:237`, `:254` at #102) sets `valid: true` and never asserts that
     `/allowance/check` isn't called. Its name promises more than it checks.
   - Fix: use `isNativeToken(chainKey, address)` from `@sodax/types` and assert `/allowance/check` isn't called.
4. nit: quote errors don't say which side. `RESTRICTED_TOKEN` (`quote.ts:250-253` on #94, `:309` at #102) says
   "that side" in nextStep with no `details.side`; `UNSUPPORTED_CHAIN` from `resolveSwapChain` has no side either.
   Fix: `details: { side }`.
5. Already fixed in the stack: on #93/#94 the shared catalog loads under the first caller's key; #95 fixes it with
   `runWithRequestContext({}, loadCatalog)`. A fake key to the live API still gets 200 today, so low impact. Only
   matters if #93 merged alone.
