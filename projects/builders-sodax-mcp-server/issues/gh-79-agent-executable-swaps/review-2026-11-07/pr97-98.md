## R0bi7's points

### (a) Oracle reads use the caller's key: confirmed, should-fix

- `usd.ts:25` calls the production oracle; the comment at `usd.ts:2` says keyless. In production,
  `SODAX_SWAP_ORACLE_BASE_URL` equals `SODAX_SOLVER_BASE_URL`, which is in `KEYED_BASE_URLS` (`http.ts:26`), so the
  oracle request carries the caller's `x-api-key`. Probe with stubbed `fetch`: `https://api.sodax.com/v1/intent/oracle`
  sent with key A.
- On canary the call goes out keyless, so the #98 canary never runs the production path.
- Cache key `"solver-oracle"` (`solver.ts:27`) is shared: prices fetched with B's key were served to A even though
  A's key was invalid.
- The 30 s backoff (`usd.ts:20-29`) is global: in the probe a 401 for A blanked B's pricing. That turns off
  `usdValue`, `usdOut` and the PRICE_OFF_MARKET refusal for every caller, and one caller can repeat it every 30 s.
- Live today the oracle answers 200 to a made-up key and to no key, so it bites only once the backend answers per
  key (401 when keys are enforced, 429 at a caller's quota). The keyless fix works now.
- Fix: `bounded(() => runWithRequestContext({}, () => getSolverOracle(SODAX_SWAP_ORACLE_BASE_URL)), …)`, or an
  explicit `forwardKey: false` option on `fetchJson`. Fix the comment.
- Test: production env, stub `fetch`, call `usdValue` inside `runWithRequestContext({ apiKey })`, assert the request
  has no `x-api-key`.

### (b) Unpriced output gets no warning: confirmed, should-fix

- With the output unpriced, the off-market check at `quote.ts:187` is skipped; `usdWarning` (`swap.ts:273`) reads
  only the input's `usdValue`.
- Probe: 5 USDC in, 1 USDC out, output unpriced → `ready` quote, no warning in `nextStep`.
- PR body says "when either side has no price it only warns": false for this case. The test "only warns when the
  output has no price" (`swapQuote.test.ts` ~558) asserts no warning at all.
- Fix: when `usdValue !== null && usdOut === null`, add a sentence like "What they receive has no USD price here, so
  the rate wasn't checked against the market: confirm the amounts with the user before anything is signed."
  Optionally `checks.market: "not_checked"` on the quote.
- Test: assert that sentence in both `price_only` and `ready`.

### (c) Redaction gaps (`logger.ts:22-53`): confirmed, should-fix

Run against a real viem 2.57.4 `HttpRequestError`:

- Request bodies stay in: the `Request body: {…from: 0xUSER…}` text survives in `message`, `stack` and
  `metaMessages`. Breaks the settled rule. Reaches logs via `actionTool.ts:39` and Discord via `notifyError`.
- Over-redaction: in ESM every stack frame is `file:///…:L:C`, so production stacks become `at f (<url>` with no
  file or line, in logs and in the Discord crash alert. `HttpError` messages also lose which route failed.
- Missed URLs: `https:\/\/` (escaped slashes) isn't matched.
- Keys never redacted: `sodax_…` keys (including inside a nested `cause`), `Bearer …`, `x-api-key` / `apiKey`
  values in error properties. URLs with userinfo or query keys are caught.
- Outside the serializer: `swapsApi.ts:296` logs upstream `apiMessage` as a plain field, no stripping (from #94).
- Fix: exclude `file:` from the URL regex; strip `Request body:` lines and `metaMessages` entries; redact
  `sodax_[A-Za-z0-9_-]{20,}` and `Bearer\s+\S+`; match `:\\/\\/`; run `withoutUrls` on `apiMessage`.
- Test: a real viem error (not `Object.assign` fakes) and an ESM stack frame.

### (d) Secret screening: confirmed, should-fix

- No false positives on real shapes: EVM addresses, EVM tx hashes, NEAR implicit (64 hex), Sui `0x`+64, Stellar
  G…/C…, bech32/taproot, ICON, Injective, token names, amounts all pass. A 20k random fuzz per shape found none. A
  64-hex `amount` is refused by design.
- False positives:
  - A Solana signature (86-88 base58) in `query`, `address` or `quoteId` is called a private key, with "move their
    funds".
  - A 64-hex token `query` on Sui (package id) or an unlisted NEAR token gets SECRET_REJECTED instead of `not_found`
    (`resolver.ts:128`). From reading the code, not run.
- False negatives:
  - The WIF, xprv, Solana, Stellar and suiprivkey rules are anchored, so any prefix text defeats them ("my key K…",
    "seed S…").
  - Not matched: `Zprv`/`Yprv`/`vprv`/`uprv`, upper-case `SUIPRIVKEY1…`, a lowercase Stellar seed.
  - Seed phrases with one typo, or words joined without separators; Japanese, Korean and Chinese phrases.
  - A Solana keypair as a JSON byte array: only zod's plain "too long" error.
  - A 64-hex key in `chain` gets UNSUPPORTED_CHAIN; with `0x` a plain "too long" zod error. Neither says the key is
    exposed.
- Fix: test the anchored shapes on each token split by `[\s,;:"'()]`; widen the xprv prefix; case-insensitive
  suiprivkey; `notHex64: "a chain"` on `chainArg` and chain fields in `NOT_HEX64_FIELDS`; a hedged refusal for the
  Solana-signature shape like `hex64Refusal`.
- Test: a pass/refuse table in `secrets.test.ts` covering every item above.

## Other findings

1. should-fix (#98, at #102): the canary signs without a minimum-received floor. `swapCanary.ts:168-172` checks the
   input amount and step shapes but never `to.minimumAmount`. With the oracle in backoff or the output unpriced, the
   script signs whatever the server built: up to 5 USDC lost per run. Fix: refuse when
   `minimumAmount < 0.97 × amount` on this USDC→USDC route.
2. should-fix (#98): no automated leak check. Neither code nor workflow has one; the plan only had a manual
   `gh run view --log`. On failure `server.log` is printed into a public log (`e2e-canary.yml:83-85`), and GitHub
   only masks exact secret strings. Fix: an `if: always()` step that greps `server.log` and the tee'd script output
   for the API key, the private key with and without `0x`, and the RPC paths.
3. nit (#98): `AMOUNT` has no upper cap (`swapCanary.ts:97`); exposure bounded only by the wallet balance.
4. nit (#98): the new drift-check step is `continue-on-error: true` on every event (`drift-check.yml:57-63`), so
   scheduled failures never go red. Make it authoritative on `schedule`.
5. process (#98): the `canary-e2e` environment doesn't exist (the API lists only `copilot`). If the workflow merges
   first, GitHub auto-creates it on the first run with no branch policy, so create it first (development only).
   Also #102 turns the switch on by default, so #98's advice to keep `SODAX_SWAP_TOOLS_ENABLED` off in production no
   longer holds once #102 merges.
6. PR body #97: "when either side has no price it only warns" is false (point b).
